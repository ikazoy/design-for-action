# 分かりやすさのウォークスルー

想定したユーザーが、実際の画面だけを手掛かりに用事を終えられるかを、一操作ずつ確かめる。
得られるのは実画面に基づく予測であり、実ユーザーの観察の代わりにはならない。

## 使う場面

分かりやすさの検証を頼まれたとき、フローや主要な画面を変更したときに使う。
小さな文言修正では使わず、SKILL.md の問いで確かめる。

## 1. 前提を書く

歩き始める前に、人物と用事の組み合わせを1〜3組に絞り、組み合わせごとに次を書く。

| 項目 | 書くこと |
|---|---|
| 人物 | 役割、製品への慣れ、知っている業務用語、権限。 |
| 用事 | 片づけたい用事と、本人が完了したと判断する条件。 |
| 状況 | きっかけ、直前の作業、端末と操作手段、時間の余裕、中断の有無。 |
| 開始地点 | どの画面と状態から始めるか、その時点で本人が知っていること。 |
| 予測 | 「この人は **X** と考えているので、**Y** の後には **Z** が起きると予想する」。 |

各項目に、根拠のある事実か仮説かを示す。
依頼、仕様、ユーザー調査に材料がなければ仮説として置き、用事や完了条件が変わる不明点だけ確認する。
人物は、世代や性別ではなく、この用事に関わる知識・権限・状況で定義する。

## 2. 画面に見えるものだけで判断する

コードや仕様を知っていると、ユーザーが持たない知識で画面を理解してしまう。
判断の根拠は、画面の表示、操作の結果、前提に書いた本人の知識に限る。
内部名、実装の都合、検証する側だけが知っている手順を根拠にしない。
コードは、問題が見つかった後の原因調査で読む。
自分で実装した直後なら、サブエージェントを使える環境では、実装の文脈を持たないエージェントに前提と実画面だけを渡す。

## 3. 一操作ずつ歩く

本人が選びそうな順に操作する。正しい経路を知っていても先回りしない。
本番データの変更、外部への送信、課金、削除など、取り消せない操作や外部に影響する操作は、実行前に確認する。

各操作で、押す前に予測を書き、次の4つを問う。

| 問い | 確かめること |
|---|---|
| 正しい目標を持てるか | 今の画面と本人の考えから、次にすべきことが分かるか。 |
| 操作に気づけるか | 探し回らずに、使う操作を見つけられるか。 |
| 操作と結果を結びつけられるか | ラベルや見た目から、望む結果につながると分かるか。 |
| 進んだと分かるか | 操作の後に、何が変わり、次に何をするか分かるか。 |

操作の後に、予測と実際を比べる。
次の形で記録し、画面の状態はスクリーンショットや操作記録として残す。

```text
操作 N：本人がすること
見えるもの：判断の手掛かりになる表示
予測：押すと何が起きると思うか
問い：目標 ○/△/×　気づき ○/△/×　結びつき ○/△/×　進捗 ○/△/×
実際：起きたこと
ズレ：予測と違った点と、本人が次にしそうなこと
```

いずれかの問いが △ か × なら、本人がしそうな誤った操作も試し、間違いに気づけるか、戻れるかを確かめる。

## 4. 範囲

入口、操作前、処理中、結果、復旧をつなげて歩く。
用事に関係するなら、空の状態、エラー、権限制限、中断からの再開、対象の画面幅と操作手段も含める。
実画面を使えないときは、スクリーンショットや仕様で問いだけを検討し、動作は未確認とする。

## 5. 報告する

用事ごとに「終えられる」「つまずくが終えられる」「終えられない」の見立てを示す。
指摘は SKILL.md の「観察できた問題 → ユーザーへの影響 → 関係する原則 → 具体的な変更」の形にし、確度を添える。

| 確度 | 意味 |
|---|---|
| 操作で確認 | 実画面で起きた事実。結果が表示されない、入力が消えるなど。 |
| 画面から推定 | 画面の表示を根拠にした、理解や迷いの予測。 |
| 実ユーザー未確認 | 前提の仮説に依存し、実ユーザーでしか確かめられない予測。 |

実行しなかった操作と表示できなかった状態は、未実行として別に挙げる。
最後に、結果を最も左右する予測を1〜3件、実ユーザーで確かめる点として残す。

## 避けること

- 感情スコア、成功率、所要時間の推定値を作らない。数値は実測があるときだけ示す。
- 架空の人物の感想を、根拠として引用しない。
- 問題が見つからなかった組み合わせを「分かりやすい」と断定しない。歩いた範囲と前提を示す。
- 歩いた後に人物像や前提を変えて、見つかった問題を消さない。変えるなら理由を書いて歩き直す。
